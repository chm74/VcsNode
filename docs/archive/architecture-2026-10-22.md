## 2. 关键结论（决定架构形状）

### 结论 1：跨网段 → 静态节点清单 + 成员主动轮询

`172.16.1.0/24` 与 `172.16.2.0/24` 是两个广播域，UDP 广播不跨三层路由传播，**自动发现不可用**，
节点清单由主节点静态维护。

实测（2026-10-22）：

| 方向 | 结果 |
|---|---|
| ICMP 98 → 1.207 | 通（RTT 0ms） |
| TCP 47820 1.207 → 98 | **通** |
| TCP 47820 98 → 1.207 | **不通**（入站被防火墙拦截） |

因此控制面采用 **成员主动轮询主节点**，不做主节点推送。只要求成员能出站，
无需在三台业务机上开任何入站端口，也避免 GPO 覆盖规则的风险。

### 结论 2：「一套系统」≠「一台机器」→ 更新单元是「服务」

set-a 横跨 207 和 145。若按「机器」为单位发版，会出现 207 已更新、145 未更新，
导致 `web/webapi` 调用旧版 `generateclient` —— 版本错配型故障，最难排查。

更新单元定义为 **Service × 目标节点集合**，并以 `set` 作为事务边界。

### 结论 3：三个目录必须分离

| 目录 | 位置 | 作用 | 权限 |
|---|---|---|---|
| **源目录** | 仅 98，如 `E:\project\web\dist` | 文件真相来源 | 98 读写 |
| **共享目录** | 98 上 `\\172.16.2.98\Tools\_vcs` | 版本仓库，写一次 | 98 写，成员读 |
| **部署目录** | 每台各自，如 `D:\vcs\app\web` | 实际运行现场 | 本地读写 |

共享目录必须落在 98（不能是各机器各自的共享），否则 98 写成员会被防火墙拦。
98 自身也走同一条链路（源目录 → 共享目录 → 98 部署目录），不做「直接部署到本地」的捷径，
否则 98 与成员是两套代码路径，回滚/审计/一致性要写两遍。

### 结论 4：98 是修改源，不做自更新

98 上改文件、改完即生效于自身，不需要「自己更新自己」。
配置为 `role: source`、`selfManage: false`，规避自更新的一整套复杂度。

### 结论 5：cmd.exe 不是进程身份

`cmd.exe` 是通用外壳，同名进程可以有几十个。且 `cmd /c start xxx.bat` 会让 cmd 立刻退出，
真正的进程是子进程 —— 监控 cmd.exe 必然误报。

进程身份 = **可执行名 + 命令行特征 + 创建时间**（指纹），且优先由 Supervisor 自己启动并持有 PID。

### 结论 6：文件更新与进程监控解耦，但共享状态

发版导致的停止必须打「预期停止」标记，否则监控会把主动停机判为崩溃并拉起旧版本，形成僵持。

### 3.1 分层职责

| 层 | 走什么 | 谁参与 | 关键约束 |
|---|---|---|---|
| L1 控制面 | HTTP 轮询 + 回执 | 成员 → 主节点（单方向） | 成员只出站，不开入站端口 |
| L2 数据面 | 共享存储文件系统 | 主节点写、成员读 | 以 sha256 校验，不信 size/mtime |
| L3 运行面 | 本地磁盘 + 进程 | 每台自治 | 发布目录只增不改，回滚零传输 |

### 3.2 部署单元模型

```
System（自动生成系统）
  └──1:N──► Component（组件）            ← 版本归因与差异判断的单位
              └──1:N──► Node 上的实例
                          ├── Release（文件快照 + sha256 + 签名）
                          └── Process（PID / 状态 / 重启次数 / 日志）

Set（一套系统）= 一组 Node 的集合        ← 事务边界
```

三个正交维度，各管一件事：

| 维度 | 回答的问题 | 粒度 |
|---|---|---|
| **System** | 现在跑的是哪个版本 | 系统级，单一 releaseId |
| **Component** | 哪些文件变了、哪个组件要重启 | 组件级 |
| **Set** | 哪些机器必须同时同版本 | 机器组 |

### 3.3 组件不是同质的（最容易建模错的地方）

「自动生成系统」由好几块内容组成，而这些块的类型不同，**不能用同一种方式管理**：

| kind | 含义 | 健康判定 | 有进程 |
|---|---|---|---|
| `service` | 常驻进程，通常有端口 | 进程存活 + 端口 + 业务探活 | ✅ |
| `task` | 一次性任务，跑完就退出 | 最近一次退出码 == 0 | ❌ 非常驻 |
| `asset` | 纯文件：模板、资产、规则配置 | 只校验文件完整性 | ❌ |
| `library` | 被宿主进程加载的库/插件 | 跟随宿主组件 | ❌ |

搞错类型的后果很具体：

- 把 `asset` 当 `service` 管 → 状态永远 `crashed`，告警噪音，最后所有人都不看告警
- 把 `task` 当 `service` 管 → 任务正常跑完退出，被判为崩溃并反复拉起，形成无限重启
- 把 `library` 当 `service` 管 → 找不到独立进程，永远「未启动」

所以配置里每个组件必须显式声明 `kind`。

### 3.4 版本是系统级的，重启是组件级的

这是本方案的核心取舍：

```
系统版本 20261022-153012-a1b2c3
  ├── web             无变化          → 不传、不重启
  ├── webapi          无变化          → 不传、不重启
  ├── generateclient  无变化          → 不传、不重启
  ├── generatetools   变更 12 文件   → 只传 12 个文件、只重启它
  └── ue_template     变更 3 文件    → 只传 3 个文件、不动进程
```

| 决策 | 选择 | 理由 |
|---|---|---|
| 版本编号 | **系统级一个** | 避免出现「组件 A v3 + 组件 B v7」的兼容矩阵；回滚时整体一致 |
| 文件传输 | 组件级增量 | 只传变化的文件 |
| 进程重启 | 组件级 | 只有受影响的组件才重启 |
| 回滚 | 系统级 | 一次退回整个系统的上一快照 |

如果改成「每个组件独立版本」，会立刻面临一个问题：207 上 webapi 是 v3 而 generatetools 是 v7，
这个组合有没有被验证过？没人知道。系统级版本把这个问题直接消掉。

### 3.5 组件依赖是 DAG，不是线性列表

组件之间的 `dependsOn` 构成有向无环图，COMMIT 顺序 = 拓扑排序：

```
generatetools ─┬─► generateclient
               ├─► webapi ──► web
               └─► (task 类组件)
```

启动/重启按拓扑序，停止按反拓扑序。若检测到环，配置直接报错退出（不要试图自动打破环）。

## 4. 一键同步流程

**场景**：98 上 `generatetools` 的产物更新了 12 个文件。

发布单位是**系统级快照**（含所有组件的清单），但差异归因和重启是**组件级**的。

```
[1] 触发      98: vcsnode push
[2] 变更检测  扫描 sources → 对比上次 manifest → 变更 { 新增 2, 修改 10, 删除 0 }
[3] 服务归因  变化文件属于 services/generatetools → 受影响服务 = { generatetools }
[4] 影响面    generatetools 部署在 98 / 149 / 145 → 目标 = { 149, 145 }（98 是源，跳过）
[5] 发布      只把 12 个变化文件写入 _vcs/releases/generatetools/<relId>/
              manifest 记录每个文件 sha256 → 用 ed25519 签名
[6] STAGE     投递任务 {op:"stage", service, releaseId, src:"\\\\172.16.2.98\\Tools\\_vcs\\..."}
              149 / 145 每 2s 轮询取到 → 本地组装新 release → 逐文件 sha256 → 回报 staged
[7] COMMIT    全部 staged 后才投递 {op:"commit"}
              成员：切 current → stop → 等端口释放 → start → healthcheck → 回报
[8] 收敛      全绿 → 记录版本、清理旧 release（保留 5 个）
              任一失败 → 对整个受影响集合投递 rollback（切回 + 重启 + 探活）
```

### 4.1 增量传输 ≠ 目录只有增量文件

两件事必须分开，否则失去回滚能力：

| | 做法 | 省的是什么 |
|---|---|---|
| **传输** | 只传变化的 12 个文件 | 网络带宽 |
| **组装** | 新 release = 上一版本整树（硬链接）+ 覆盖 12 个文件 | 本地磁盘 IO |

即 rsync `--link-dest` 思路。未变文件硬链接指向上一版本，不复制、不传输、不占额外空间。
每个 release 都是完整可运行目录，回滚只需切指针。
Windows 硬链接要求同卷，跨卷自动降级为复制（`sync.assemble: hardlink | copy`）。

### 4.2 为什么必须两阶段（STAGE / COMMIT）

若一台一台走完全流程：

```
207: 传输 → 重启 → 成功
145: 传输 → 失败
结果：207 新版 + 145 旧版 → 版本错配
```

两阶段把「慢且易失败」与「快但不可逆」分离：

| 阶段 | 耗时 | 失败概率 | 失败代价 |
|---|---|---|---|
| STAGE（并行） | 秒级~十几秒 | 主要失败点（磁盘/权限/共享不可读） | 零影响，服务仍跑旧版 |
| COMMIT（按依赖序） | 1~2s/台 | 较低 | 需回滚，仅切指针 + 重启 |

### 4.3 COMMIT 顺序（按依赖方向）

```
1. 145: generateclient · generatetools   底层生成服务
2. 207: webapi                           依赖生成服务
3. 207: web                              前端，最后切
```

set-b / set-c 是单机全套，内部也按此顺序 restart。

### 4.4 变更检测时机

不建议默认开实时监听：构建是渐进写文件的过程，监听会捕捉到「构建到一半」的状态。

```yaml
sync:
  trigger: manual        # 构建完成后手动 push（默认）
  watchDebounceMs: 10000 # 若开 watch，停止变化 10s 后才认为稳定
```

## 5. 目录与配置

完整配置见 **`config/vcsnode.yaml`**。

| 段 | 内容 | 成员是否需要 |
|---|---|---|
| `cluster` | 主节点地址、密钥、轮询间隔、允许网段 | 需要 |
| `monitor` | 采样间隔、健康判定条件、自愈策略 | 需要 |
| `services` | 启动命令、端口、健康检查、进程指纹 | 需要 |
| `sources` | 源目录 → 服务映射 | 仅 98 |
| `nodes` | 机器清单 + 每台的服务与本地路径 | 仅 98 |
| `sets` | 事务边界 | 仅 98 |

### 5.1 共享目录布局

现有共享 `\\172.16.2.98\Tools` 中已有内容一律不碰，所有写入限制在 `_vcs` 子目录：

```
\\172.16.2.98\Tools\
  AutomationUE5.3\             ┐
  logs\                        │ 现有内容，只读不碰
  _deployment_backups\         │
  *.zip  *.rar                 ┘
  _vcs\                        ← 唯一写入区
    releases\<service>\<releaseId>\
    manifests\<releaseId>.json
    manifests\<releaseId>.json.sig
    keys\private.pem           ← 仅 98 可读
    tmp\
```

### 5.2 三条硬规则（代码强制，不可配置覆盖）

1. 写入路径 `realpath` 后必须以 `<sharedRoot>\_vcs\` 为前缀，否则拒绝。防 `..` 逃逸与符号链接穿越。
2. GC 只允许删除 `_vcs\releases\<service>\<releaseId>\` 且 `releaseId` 匹配 `^\d{8}-\d{6}$`，其余跳过并告警。
3. `_vcs` 在扫描源中永远排除，防止「扫描 → 写入 → 再扫描」自引用。

### 5.3 权限现实与对冲

实测成员机对 `Tools` 有写权限，因此不能依赖 ACL 防篡改：

| 风险 | 概率 | 对策 |
|---|---|---|
| 误删 / 误覆盖发布内容 | 中 | 目录隔离 + 三条硬规则 |
| 伪造发布内容 | 低 | manifest 用 ed25519 签名，成员验证通过才落盘 |

签名方案：98 独占私钥，成员内置公钥。即使成员能写共享，没有私钥也构造不出他人接受的 manifest。
（HMAC 共享密钥做不到——验证方必然持有密钥，也就能伪造。）

### 5.4 节点侧目录

```
<localRoot>\<service>\
  releases\<yyyyMMdd-HHmmss>\
  current -> releases\<...>        （Windows 用 current.txt 指针）
  shared\logs\
  .vcs\state.json  .vcs\audit.log
```

**必须按服务分目录，不能按机器分**：207 上同时跑 web 和 webapi，两者版本与回滚必须独立。

## 6. 进程监控（cmd.exe 场景）

### 6.1 三层健康判定

只有「进程存在」远远不够，这是运维工具最常见的假正常来源：

| 判定层 | 检测方式 | 失败含义 |
|---|---|---|
| **L1 进程** | PID 存活 + 命令行指纹匹配 | 进程死了 / 被顶替 |
| **L2 端口** | `Get-NetTCPConnection -State Listen` 含该端口 | 进程在但服务没起来 |
| **L3 业务** | HTTP 探活 / 自定义命令 | 进程和端口都在，业务挂了 |

| L1 | L2 | L3 | 状态 | 处理 |
|---|---|---|---|---|
| ✅ | ✅ | ✅ | `running` | 无 |
| ✅ | ✅ | ❌ | `unhealthy` | 告警，可选重启 |
| ✅ | ❌ | — | `starting` / `stuck` | 启动超时后重启 |
| ❌ | — | — | `crashed` | 按策略拉起 |
| — | ✅ | — | `orphan` | 端口被他人占用，人工介入 |

`orphan` 很关键：进程没了但端口还在监听，盲目重启只会一直失败。

### 6.2 由 Supervisor 启动，而不是事后猜

```
Supervisor.spawn("cmd", ["/c", "启动.bat"], { cwd: current, detached: true })
  → 拿到 pid → 写 pidfile（pid + 启动时间 + cmdline 指纹）
  → 监控 = PID 存活 + 端口监听
```

好处：PID 已知、进程树可控（停止时 `taskkill /PID x /T /F`）、重启次数与退出码可查。
命令行指纹只用于校验「进程没被顶替」以及 adopt 已存在的旧进程。

### 6.3 采样实现与成本

Windows 取命令行只有 CIM 一条路（`wmic` 已废弃）：

```powershell
Get-CimInstance Win32_Process |
  Select-Object ProcessId, ParentProcessId, Name, CommandLine, CreationDate, WorkingSetSize
```

从 Node 调用每次约 200~500ms，因此：

- 采样间隔 ≥ 5s（10s 更稳），单核占用约 4~8%
- **一次采样覆盖所有服务**，不按服务逐个调用
- 结果在 Agent 内缓存，上报时读缓存
- 只查本机，不跨机器 WMI（跨机要开 RPC 端口，正好撞防火墙）

### 6.4 自愈策略

```yaml
monitor:
  intervalMs: 5000
  require: [process, port]
  restart:
    policy: on-failure     # never | on-failure | always
    maxAttempts: 5         # 10 分钟窗口内最多 5 次
    windowMs: 600000
    backoffMs: 2000        # 2s → 4s → 8s → 16s → 32s
```

超过上限后置为 `failed` 并停止自动重启。宁可人工介入，也不要无限重启——
无限重启会刷爆日志、占满 CPU，反而更难排查。

### 6.6 与文件更新的协同

| 场景 | 是否重启 | 说明 |
|---|---|---|
| 监控发现 `crashed` | ✅ 自动 | 与发版无关的独立自愈 |
| 发版 deploy | ✅ 主动 | 先标记 `expectedStop = true`，自愈跳过 |
| 只同步静态资源 | ❌ | reload 或人工决定 |

`expectedStop` 标记是必须的，否则换版本时监控会立刻判定崩溃并把旧版本拉起来。
