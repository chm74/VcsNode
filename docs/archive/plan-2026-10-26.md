## 0. 需求对齐

| # | 原始诉求 | 落点 | 状态 |
| --- | --- | --- | --- |
| 1 | 98 作主节点，集中管理 145 / 207 / 149 的服务状态，能看状态、能启动停止 | 控制面（3）+ 进程管理（5）+ 监控（6）：主节点持有全部状态与指令入口，成员只执行 | 已定 |
| 2 | 更新文件写入统一共享目录，主节点一键分发到其他机器 | 数据面（4）+ 一键同步（7）：98 写一次共享，成员按 manifest 只拉变化文件 | 已定，路径待核准 |
| 3 | 轻量：3~4 个 Node 服务，各自监测本机进程，网络回报主节点，不用数据库 | 4 个进程（每台 1 个），主节点 = 管理端 + 本机 agent 合一；状态存内存 + JSON 快照 | 已定，见第 9 节 |

一句话概括形态：

```
4 台机器 = 4 个 Node 进程，没有一个数据库、没有一个消息队列、没有一个反向隧道。
98 上那一个多担一个角色：它同时是「管理端」和「98 自己的 agent」。
```

## 3. 控制面：成员保持一条出站连接，98 沿它下发

```
        98（主节点）                                   成员（207/145/149）
        ├─ 事件流   GET /api/agent/stream?since=<seq>  ←── 常驻（SSE）
        └─ 状态汇总 POST /api/agent/report             ←── 按需
```

**方向没变，形态变了。** 仍然由成员发起、仍然不开任何入站端口（防火墙限制不变），
但连接不是「每隔 2s 来问一次」，而是**建立后一直握着**，98 有指令时直接沿这条连接推下去。
这就是「98 下达命令，成员立刻收到」，延迟从「0~2s」降到「一个 RTT（<10ms）」。

### 3.1 为什么不是固定间隔轮询

| | 2s 轮询 | 常驻连接（SSE） |
| --- | --- | --- |
| 首次延迟 | 0~2s，平均 1s | 一个 RTT |
| 空闲开销 | 3 台 × 43,200 次/天 | 1 次/台，之后只有心跳 |
| 失联发现 | 心跳超时 3 次 ≈ 6s | 连接断开即知 |
| 丢指令风险 | 有：两次请求之间存在窗口 | 无：序号游标保证不丢不重 |

轮询不是「错」，是**在最省事的实现下能接受的折中**。既然成员本来就在跑我们的 agent，
把这条 HTTP 请求挂住不返回，成本几乎为零，没必要为省这点代码牺牲延迟和正确性。

### 3.2 关键设计：序号游标

```
成员：GET /api/agent/stream?node=145&since=41
98 ：若队列里有 seq > 41 的指令 → 立即推送；否则挂起等待
     event: task      { seq: 42, id: "...", kind: "stop", ... }
     event: ping      （15s 一次，保活）
     event: bye       （主节点重启/升级，成员按退避重连）
```

`since` 是必须的。没有游标就只能返回「当前队列状态」，成员重启或断线重连时
会漏掉在这期间下发的指令 —— 而且这种漏是静默的，只有到现场才发现某台机器没停干净。

### 3.3 断线与重连

```
1s → 2s → 5s → 10s → 30s（封顶，加 0~30% 抖动，避免三台同时重连打爆 98）
```

- 98 侧：连接断开 → 立刻把该节点标为 `node-offline`（不用再等心跳超时）
- 成员侧：45s 收不到任何字节（含 ping）→ 主动重连；防止中间设备静默黑洞
- 收到 `bye` → 立即重连，不等超时

### 3.4 备选与不选项

| 方案 | 判断 |
| --- | --- |
| **长轮询**（挂 25s 后返回空） | 可接受。若现场链路对长连接不友好（NAT 超时短、防火墙杀空闲），切这个，接口不变 |
| **WebSocket** | 不必要。我们要的是单向下发 + 单向回报，WS 的双工能力和帧协议都是额外负担 |
| **FileSystemWatcher 监听共享目录** | 不选。SMB 的 CHANGE_NOTIFY 会丢事件、缓冲区会溢出，且要额外占 445；一旦漏事件就是静默失效 |
| **反向隧道**（成员开 SSH/RDP 通道给 98） | 不选。运维负担远大于收益，等于在防火墙上凿洞 |

### 3.5 数据面仍走各自的通道

事件流只送**指令**（几 KB），不送文件。文件仍然由成员从 `\\172.16.2.98\Tools\_vcs`
按 manifest 拉取 —— 控制面和数据面分开，一条连接卡住不影响另一条。

- 98 自己的组件由本地 Supervisor 直接控制，不走队列，零延迟。
- 界面用三态表示：`dispatched / executing / confirmed`。

## 4. 文件同步

### 4.1 原则

1. **只传变化的文件**（sha256 比对），从不传整个目录。
2. **两条落地策略**，由「改了之后是否需要重启才生效」决定：

| 判据 | 策略 | 适用 |
| --- | --- | --- |
| 下一次读取即生效 | `in-place`：临时文件 + 原子替换 + 备份 | `tools`、`ue_templates`、`web`、`shp_*` |
| 必须重启才生效 | `release-switch`：新目录 + 切指针 + 重启 | `webapi`、`generateclient`、`generatetool` |

3. `in-place` 的原子替换保证读方只会看到完整旧文件或完整新文件：

```
写 <name>.vcsnew → 校验 sha256 → 备份原件到 _vcs/backup/<relId>/
→ MoveFileEx(REPLACE_EXISTING) → 记入 manifest
```

4. `release-switch` 的新目录用**硬链接**复用上一版未变文件：
   网络只走变化文件，磁盘几乎不增长，每个 release 都是完整可运行目录。

### 4.2 两阶段：STAGE / COMMIT

```
[STAGE]  服务照常运行，业务无感
  98 写变化文件到 \\172.16.2.98\Tools\_vcs\releases\<组件>\<relId>\
  manifest 记录每文件 sha256，ed25519 签名
  成员收到指令 → 拉到本地 releases\<组件>\<relId>\
                → 组装（硬链接未变文件）
                → 执行构建：dotnet build -c Release / npm 依赖检查
                → 逐文件校验 → 回报 staged

[COMMIT] 每台 1~3 秒
  确认无运行中任务 → expectedStop = true
  → stop 进程 → 切 junction → start 进程 → 探活 → 回报
```

**为什么必须两阶段**：把「慢且易失败」的传输/构建放在服务运行期，
「快但不可逆」的切换只占 1~3 秒。传输失败时服务完全没被触碰，代价为零。

**为什么构建要在 STAGE**：源码运行模式下，`dotnet run` 含编译（10~30s）。
放到 COMMIT 会把停机窗口撑大一个数量级。因此 STAGE 里先 `dotnet build`，
COMMIT 时直接 `dotnet <组件>.dll` 启动。

### 4.3 回滚

| 策略 | 回滚动作 |
| --- | --- |
| `release-switch` | 切回上一 release 指针 + 重启，零传输 |
| `in-place` | 按 manifest 从 `_vcs/backup/<relId>/` 逐文件还原 |

### 4.4 排除清单（硬性）

| 排除 | 原因 |
| --- | --- |
| `appsettings.json` | **各机 IP / 路径 / 数据库不同，同步会直接写坏目标机** |
| `nlog.config` | 同上，日志路径各机不同 |
| `public/config.js` | 前端的运行时配置：`WSURL` 指向本机后端，与后端 `appsettings.json` 同性质 |
| `node_modules/`、`.venv/` | 各机自行安装（`.venv` 内含绝对路径，跨机复制必坏） |
| `bin/`、`obj/` | 本机编译产物 |
| `*.Tests/`、`SceneAutoApply.PreviewBlocks.Tests` | 测试工程不同步 |
| `NLogs/`、`logs/`、`App_Data/*` | 运行期日志与缓存 |
| `*.zip` `*.rar` 等大包 | 除 `TP_TuguanStreaming.zip` / `TP_TuguanStreamingV5.zip` 外一律不同步 |

**`appsettings.json` 这条是硬伤**：仓库里它随代码一起提交（`a076978` 就改过它）。
如果按组件整目录同步，145 的 `SignalRUrl` 会被写成 98 的值，目标机当场连错后端。

排除不是丢弃：仓库版本仍会传到 release，只是改名为 `appsettings.repo.json` 供对比，
生效的始终是各机自己那份（见 8.3 ②）。

### 4.5 已知的「文件之外」的变更

`a076978` 新增了 3 个 DbSet（`PreviewBlockSnapshots` / `PreviewBlockCollections` /
`PreviewBlockSaveReceipts`），但仓库里既没有 Migrations 目录，也没有建表 SQL。

→ **有些版本不是纯文件变更**。同步流程里必须留一道人工闸门，
不能「点一下就把 4 台机器全部同步完」。

### 4.6 成员怎么读共享：UNC 直连，不映射盘符

```powershell
# 成员端：直接用 UNC，不做 net use
Copy-Item '\\172.16.2.98\Tools\_vcs\releases\webapi\vcs-20261026-01\app.js' -Destination ...
```

**为什么不用盘符映射**

- 盘符是「登录会话」级别的，`net use Z:` 只对当前交互用户有效；
  以服务 / 计划任务身份运行时看不到那个 Z 盘
- UNC 没有挂载这一步，也没有「重启后映射丢了」的问题
- 权限模型直接走访问者凭据，不依赖谁先登录过

**为什么 98 写也是 SMB 但不用额外处理**：`MoveFileEx(REPLACE_EXISTING)` 和
`File.Replace` 在 SMB 上由服务端执行 rename，对读者是原子的 —— 不会读到半个文件。
这正是 `in-place` 策略能成立的前提。

**三个必须处理的现实问题**

| 问题 | 说明 | 处置 |
| --- | --- | --- |
| 进程身份 | agent 以 LocalSystem 跑时，SMB 用的是**机器账号** `COMPUTERNAME$`，通常被拒。表现为「命令行里能读、装成服务就读不到」 | 用专用账号运行 agent；或 `cmdkey /add:172.16.2.98` 在该账号下存凭据 |
| 主机名解析 | 跨网段 NetBIOS/WINS 不可靠，`\\SCENE-98\Tools` 时通时不通 | 一律写 IP：`\\172.16.2.98\Tools` |
| 权限过宽 | 实测该共享可写。成员只该读 | 建 `vcsnode-ro`（Read）给成员、`vcsnode-rw` 给 98；只开 445，不开 139 |

验证脚本：`tools/smb-probe.ps1`（默认只读；`-TestWrite` 才试探写入）。

**备选方案（暂不采用）**：既然成员本来就要连 `98:47820` 并常驻，把文件分发也做成
同一个端口的 HTTP 下载，就只需要开一个端口、复用已有的 HMAC 鉴权、完全绕开 SMB ACL
与身份问题。代价是要自己实现断点续传与缓存，且运维不能再用资源管理器直接翻共享目录。
当前选 SMB，是因为它可读可查、可控性对现场更友好；若 445 跨网段被拦且无法放行，
再切 HTTP 方案。

## 5. 进程管理

### 5.1 持有方式

Supervisor 自己 spawn、自己持有：

```
pid + 进程创建时间 + 命令行哈希  = 指纹（防 PID 复用杀错进程）
状态机：stopped → starting → running → stopping → stopped | crashed | orphan
```

**阶段一用 `adopt` 接管现有人工启动的进程**（按指纹认领），只做监控和手动停启；
稳定后再切到 Supervisor 自己 spawn，避免一上来打断现场作业。

### 5.2 启动

```
1. 已在 running → no-op（幂等）
2. 检查 dependsOn 健康
3. spawn（detached + windowsHide + stdout/stderr 重定向到 logs/<组件>/<日期>.log）
4. 记指纹，状态 → starting
5. 等就绪：HTTP 200 / 端口 Listen / SignalR 连接建立
6. 超时 → failed（不无限等）
```

### 5.3 停止

```
1. 打 expectedStop = true（否则自愈会立刻拉起旧进程）
2. 检查是否忙 ← 关键，见 5.4
3. taskkill /PID <pid>            （先礼，不带 /F）
4. 等待 N 秒
5. 仍存活 → taskkill /PID <pid> /T /F   （/T 必须，否则留下 python/UE 孤儿）
6. 验证端口释放；未释放 → 标 orphan，禁止自动重启
7. 状态 → stopped
```

> 已知缺陷：`generateclient` / `generatetool` 虽有 `Ctrl+C` 清理钩子，但外部无法
> 可靠投递 `CTRL_C_EVENT`，实际会退化为硬杀。若要真优雅停，需给它们加本机停机信号。

### 5.4 忙碌保护（最重要）

运维手册明确：停止生成必须走系统停止入口，避免状态不一致。
`generateclient` 会向 webapi 推送 `SendStateToServer(isBusy)`。

`stop` / `restart` / 发版 COMMIT 前必须确认空闲：

| 方案 | 是否改代码 | 可靠性 |
| --- | --- | --- |
| A. webapi 增加只读接口 `/api/clients/state` | 要 | 高（推荐） |
| B. 观察任务目录最近写入时间 | 不用 | 中（过渡方案） |
| C. 查数据库队列 | 不用但耦合 | 中 |

**忙的时候不重启**：宁可让同步排队等待，也不把正在生成的项目弄坏。

### 5.5 顺序与并发

```
启动：webapi → (shp_plants, shp_buildings, generatetool) → generateclient → web
停止：反序
```

- set 内串行，跨 set 并行
- 组件级互斥锁，避免两条指令打架
- 所有动作幂等

### 5.6 自愈

| 情况 | 处置 |
| --- | --- |
| 崩溃（退出码 ≠ 0） | 按 `on-failure` 拉起，5 次 / 10 分钟，退避 2s |
| 人工停止 / 发版停止 | `expectedStop` 期间不拉起 |
| 进程没了但端口被占 | 标 `orphan`，禁止自动重启，先列出占用者 |
| 超过重试上限 | 停止自愈 + 告警 |

## 6. 监控

### 6.1 分工

| | 98 | 成员 agent |
| --- | --- | --- |
| 采样 | 只采本机 | 采本机全部组件 |
| 判定 | **全部判定在 98**（规则集中，改规则不用重发 agent） | 只上报原始观测 |
| 处置 | 决定并下发指令 | 执行指令 |

### 6.2 节奏

| 项 | 间隔 | 说明 |
| --- | --- | --- |
| 控制面连接 | 常驻 | 一条 SSE 长连接，15s 一个 ping；**它同时就是心跳**，不用另外发 |
| 状态上报 | 变化时 + 30s | 组件状态没变就不发，只报版本与时间戳 |
| 进程采样 | ≥5s | 宿 PowerShell 取 `CommandLine` 每次 200~500ms，一次采样覆盖全部组件 |

控制面连接兼任心跳之后，少了一路独立的心跳，也少了一套「心跳超时」的判定逻辑：
**连接断开 = 节点失联**，判定依据从「时间推断」变成「事实」。

### 6.3 四种状态（必须区分）

| 状态 | 依据 | 处置 |
| --- | --- | --- |
| `node-offline` | 控制面连接不存在（非正常断开 + 重连失败） | 只告警，**不重启**（重启指令没人接） |
| `crashed` | 连接正常，进程不在 | 拉起 |
| `orphan` | 进程不在但端口被占 | 不重启，先查占用 |
| `degraded` | 进程在，SignalR 连接断 | 重启客户端 |

### 6.4 各组件的判活方式

| 组件 | 判活 |
| --- | --- |
| `web` | TCP 端口 + HTTP GET `/` 200 |
| `webapi` | TCP 3601 + HTTP GET `/swagger/index.html` 200 |
| `generateclient` | 进程存活 + 到 `3601` 的 ESTABLISHED 连接 |
| `generatetool` | 同上 |
| `shp_plants` / `shp_buildings` | TCP 4000 / 4001 |
| `aigenerate` | TCP 5231 + HTTP GET `/swagger/index.html` |
| `tools` / `ue_templates` | 不判活（纯文件） |

## 7. 一次完整同步（端到端）

```
1. 98 改代码（服务未运行）
2. vcsnode push
3. 扫描 → 差异 → 组件归因 → 影响面
     web +5198/-194 → 组件 web
     webapi +3109    → 组件 webapi
     GenerateClient  → 组件 generateclient
     AutomationUE5.3 → 组件 tools（asset）
4. 人工闸门：确认本次是否含数据库变更（如本次需建 PreviewBlock* 三张表）
5. STAGE：写共享目录 → 成员拉取 + 构建 + 校验 → 回报 staged
6. COMMIT（按依赖序）：
     generateclient → webapi → web
     每台：查忙 → expectedStop → stop → 切 → start → 探活
7. 收敛：全绿则记版本、GC 旧 release（保留 5 个）
   任一失败 → 整个受影响集合回滚
```

### 8.3 `dotnet xxx.dll` 带出的三个硬约束

**① 配置文件按「当前工作目录」解析，不是按 DLL 目录**

```csharp
// GenerateClient/Utils/ConfigHelper.cs:43、GenerateTool/Utils/ConfigHelper.cs:39
.SetBasePath(Directory.GetCurrentDirectory())
.AddJsonFile("appsettings.json", optional: false, ...)
```

`webapi` 用 `WebApplication.CreateBuilder()`，ContentRoot 同样是当前工作目录。
`optional: false` 意味着 **cwd 里没有 `appsettings.json` 就直接启动失败**。

所以 `cwd` 不是可有可无的细节，它是运行语义的一部分 —— 监控里采集进程工作目录，
不只是为了好看。

**② `dotnet build` 会用仓库版本覆盖本机配置**

`GenerateClient.csproj` / `GenerateTool.csproj` 都写了：

```xml
<Content Include="appsettings.json">
  <CopyToOutputDirectory>PreserveNewest</CopyToOutputDirectory>
</Content>
```

每次构建都会把仓库里的 `appsettings.json` 复制到输出目录。145 上手工改对的
`SignalRUrl` 会在下一次构建时被悄悄改回 `145:3601`，而服务照样能起来、日志也不报错，
只是连不上后端 —— 典型的「同步后一周才发现」。

**处置**：不要依赖输出目录里的那份配置。

```yaml
stage:
  build:
    cmd: dotnet
    args: ["build", "<csproj>", "-c", "Release", "-o", "bin"]   # 产物集中到 bin/
start:
  cmd: dotnet
  args: ["bin/<Xxx>.dll"]
  cwd: "."                                                     # 根目录
localConfig: ["appsettings.json", "nlog.config"]                # 构建后再回填到根目录
```

- 构建产物一律进 `bin/`，本机配置放在 release 根目录，两者物理隔离，构建永远碰不到它
- 回填来源是 `D:\SceneAutomationV3\_config\<组件>\`，各机自己维护，永不参与同步
- 仓库版本仍然会传过来，但改名存为 `appsettings.repo.json`，STAGE 阶段对比键集，
  新增配置项会提示「仓库多了 X 个键，请手工合入本机配置」

这样既不丢新配置项，也不会写坏目标机。

**③ `launchSettings.json` 对 `dotnet xxx.dll` 不生效**

仓库里 webapi 的 `applicationUrl` 是 `http://*:3601`，但那只在 `dotnet run` 时生效。
`dotnet SceneAutoApply.dll` 不读它，不给地址就默认 `http://localhost:5000` ——
本机自测能通、别的机器连不上。

**处置**：启动命令显式注入 `ASPNETCORE_URLS=http://0.0.0.0:3601`。

### 8.4 前端端口对不上（待现场核对一条命令即可）

`vite.config.ts` 里写死 `port: 3333`、`strictPort: false`。而手册说 207 用 3071。

如果 207 上就是纯 `npm run dev`，实际监听的是 3333；如果监听 3071，那 207 上的
`vite.config.ts` 被改过 —— 那它也该进 `localConfig`，否则下次同步会把 3071 改回 3333。

**处置**（不依赖现场答案）：启动时显式传端口并加 `--strictPort`。

```yaml
args: ["run", "dev", "--", "--port", "{port}", "--strictPort"]
```

`strictPort` 很关键：不写的话端口被占时 vite 会**静默换一个端口**继续跑，
健康检查报错但进程看着正常，排查方向全错。

端口的真实值仍需在 207 上确认一次：`Get-NetTCPConnection -State Listen` 看 3071 还是 3333。

### 8.5 仓库路径 ≠ 部署路径（已有先例）

仓库里 `Tools/update_changed_tools_to_v3.ps1` 已经在做「只同步变化文件到
`D:\SceneAutomationV3\Tools`」，可以作为现有约定的证据：

| 仓库路径 | 部署路径 |
| --- | --- |
| `Tools/**` | `D:\SceneAutomationV3\Tools\**` |
| `Unreal脚本/AutomationUE5.3/**` | `Tools\AutomationUE5.3\**` |
| `CityEngine脚本/SceneAutomationGeneration/**` | `Tools\SceneAutomationGeneration\**` |
| `CityEngine脚本/…/CEScripts/startup.py` | **额外**再写一份到 `Tools\CE_Template\startup.py` |
| `…/CEScripts/AutoCE.py` | **额外**再写一份到 `Tools\CE_Template\CETemplate\scripts\AutoCE.py` |

最后两行是关键：**一个仓库文件对应两个部署文件**。同步模型必须支持 1→N 映射，
不能假设「一个源文件只有一个落地位置」。这也解释了为什么单纯比目录树不够。

## 9. 进程与模块划分（4 个 Node 进程，无数据库）

### 9.1 进程清单

| 进程 | 位置 | 端口 | 职责 |
| --- | --- | --- | --- |
| `vcs-master` | 98 | 47820（入站） | Web UI · REST API · SSE 下发 · 指令队列 · 状态汇总 · 判定引擎 · 同步编排（STAGE/COMMIT）· **本机 agent 角色** |
| `vcs-agent` | 207 | 无入站 | 常驻连 98 · 采样本机进程 · 执行指令 · 本地日志 |
| `vcs-agent` | 145 | 无入站 | 同上 |
| `vcs-agent` | 149 | 无入站 | 同上 |

主节点不额外起第五个进程：它把 `agent` 模块**在同一进程内**加载，管理自己那 6 个组件。
所以「4 台机器 = 4 个进程」，和「3~4 个 Node 服务」的要求一致。

### 9.2 代码结构（单仓、两个入口、零外部依赖）

```
vcsNode/
├── src/
│   ├── core/      配置解析 · 哈希 · manifest · 原子写 · 锁 · 日志
│   ├── agent/     supervisor（启停/指纹/查忙）· 采样（PowerShell）· 指令执行
│   ├── master/    http api · sse · 队列 · 判定 · 同步编排 · 静态 UI
│   └── proto/     信封格式 · 序号 · HMAC
├── bin/
│   ├── master.mjs     只在 98 跑
│   └── agent.mjs      三台成员跑
└── ui/            单页，无构建步骤
```

**零外部依赖**是有意的：现场机器未必能连外网 `npm install`。
只用 `node:http` / `node:fs` / `node:crypto` / `node:child_process`，SSE 是普通 HTTP，
不需要 `ws`。部署方式就是拷贝目录 + `node bin/agent.mjs`。

### 9.3 不用数据库，状态怎么存

| 数据 | 存放 | 说明 |
| --- | --- | --- |
| 各机组件状态 | 内存 Map | 唯一真相在内存，读时不落盘 |
| 待执行指令 + 序号 | `state/queue.json` | 原子写（临时文件 + rename），重启续号 |
| 已确认指令 | `state/queue.json` 滚动保留最近 500 条 | 够排查即可，不做历史归档 |
| 同步记录 | `state/releases.json` | releaseId → 文件清单摘要 → 各机落地状态 |
| 事件流水 | `logs/events-YYYYMMDD.jsonl` | 追加写，一天一个文件，便于 grep |

写入频率是「分钟级、几 KB」，JSON + 原子 rename 完全够用。引入数据库反而增加现场部署成本，
而 98 上那套 PostgreSQL 是业务库，vcsNode 不该去耦合它。

**代价**：没有事务。所以要求所有指令**幂等** —— `start` 已在运行就返回成功、
`stop` 已停止就返回成功、`commit` 重复执行结果一致。这样才能在崩溃重启后安全重放队列。

### 9.4 共享目录与本地路径都按节点配（现场四台可能不一致）

需求里提到「四台机器的共享目录有可能不一样」，所以路径**不能写成一个全局常量**。
配置分三层，越靠下优先级越高：

| 层 | 内容 | 谁维护 |
| --- | --- | --- |
| ① 组件默认 | 组件该有什么、怎么启动、怎么判活、默认端口 | 98，配置页 |
| ② 节点覆盖 | 该节点上这个组件的 `localRoot` / `port` / 是否启用；该节点看到的 `sharedRoot` | 98，配置页 |
| ③ 本机引导 | `master` 地址、`nodeId`、`secret`、缓存目录 | **各机本地文件，永不被下发覆盖** |

```yaml
# ① 全局默认
storage:
  sharedRoot: '\\172.16.2.98\Tools'

# ② 节点覆盖：该机自己看到的共享路径可能不同
nodes:
  172.16.1.145:
    storage:
      sharedRoot: '\\172.16.2.98\sense_automation_v3\tools'   # 例如共享名不同
    components:
      generateclient:
        localRoot: 'E:\SceneAutomationV3\GenerateClient'      # 例如盘符不同
  172.16.1.207:
    storage:
      sharedRoot: 'Z:\Tools'                                  # 例如用映射盘（能通就行）
```

**为什么第 ③ 层不能下发**：agent 得先知道「连哪台主节点」，才能收到配置。
这一层下发不了，也不该下发 —— 主节点地址写错就是全盘失联，没有第二条路回来。
所以它是各机上一个手写一次的小文件：

```json
{ "master": "172.16.2.98:47820", "nodeId": "node-145", "secret": "…", "cacheDir": "C:\\vcsNode\\state" }
```

其余一切（有哪些组件、装在哪、共享目录在哪）全部由主节点下发。

### 9.5 配置页（一次配置四台，而不是逐台远程桌面改）

矩阵形态：**行 = 组件，列 = 机器**，单元格 = `启用 / localRoot / port`。

```
            98        207       145       149
web         ●3333     ●3071     –         ●3333
webapi      ●3601     ●3601     –         ●3601
generateclient ●      –         ●         ●
generatetool   ●      –         ●         ●
shp_plants  ●4000     –         ●4000     ●4000
tools       ●         –         ●         ●
        ─────────────────────────────────────
共享目录    D:\…\Tools  \\…\Tools  \\…\v3\tools  \\…\Tools
```

页面上必须有五个动作，否则「统一配置」会变成「统一配错」：

| 动作 | 作用 |
| --- | --- |
| **逐格编辑 + 整列复制** | 145 和 149 配置相近时，一键复制再改两处盘符 |
| **探测**（每节点一个按钮） | 在该机上实际执行：路径是否存在、是否可读、`.venv` 是否存在、端口是否被占、共享是否可读。结果回显到格子里 |
| **保存前 diff** | 「将修改 207 的 web.port、145 的 sharedRoot」，逐条列出，确认才生效 |
| **下发并等确认** | 逐台下发，收到 ack 才算成功；超时的机器标黄，不阻塞其他机器 |
| **漂移提示** | agent 上报自己正在用的 `configRevision`，与主节点不一致的机器高亮 |

探测这一步是关键：配置页最容易犯的错是「保存成功但机器上根本不存在这个路径」。
没有探测，错误要等到下一次同步时才暴露，而那时正在停机窗口里。

### 9.6 版本、回退与失败保护

```
主节点保存 → revision+1 → 写入 state/config.json（原子写）
           → 沿 SSE 下发 event: config { revision, payload, hmac }
           → agent 校验签名 → 写入 state/config.<rev>.json
           → 自检（路径是否存在、能否读共享）
           → 全部通过 → 切换为生效配置，回 ack
           → 任一失败 → 保留旧配置继续跑，回 nack + 具体原因
```

三条保护：

1. **fail-safe**：配置下发失败不影响运行。agent 永远保留 `config.last-good.json`，
   主节点挂了也能用最后一份配置继续管理本机进程
2. **可回退**：保留最近 10 个 revision，页面上一键回退
3. **拒绝破坏性配置**：`localRoot` 指向不存在的路径、或两个组件指向同一目录（会让变更归因错乱），保存时直接拦下

### 9.7 接口只有四个

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| `GET` | `/api/agent/stream?since=<seq>` | 成员常驻连接，98 沿它推指令与配置 |
| `POST` | `/api/agent/report` | 成员上报状态、探测结果、执行结果 |
| `GET` / `POST` | `/api/ui/*` | 管理端：状态、配置、指令、同步 |
| `GET` | `/` | 单页管理界面 |

鉴权：一个预共享密钥 + HMAC 签名（`cluster.secret`），所有请求带时间戳与签名，
时间窗 5 分钟防重放。不需要账号体系。

### 9.8 实现顺序（四步，每步单独可验收）

| 步骤 | 交付 | 对现场的价值 | 风险 |
| --- | --- | --- | --- |
| 1 | agent 骨架 + 进程采样 + 上报；98 显示 4 台机器的进程清单（配置先读静态文件） | 先看清现状，尤其「进程在但 SignalR 断」这类隐藏故障 | 纯只读，不碰任何服务 |
| 2 | 主节点 API + SSE + 状态页 + **配置页（矩阵 / 探测 / diff / 下发 / 回退）** | 一次把四台的路径配齐，替代逐台改配置 | 仍只读；配置模型先定，UI 后加 |
| 3 | supervisor 启停 + 查忙保护 | 远程停启，且不会打断正在跑的生成任务 | 第一次会动进程，先在 98 自测 |
| 4 | 扫描 + manifest + STAGE/COMMIT + 一键同步 | 「主节点改完，一键同步到三台」 | 最大的块，独立验收 |

第 1 步读静态配置文件（就是现在的 `config/vcsnode.yaml`），schema 直接按上面三层设计，
第 2 步的配置页只是给同一份数据加个编辑器 —— **配置模型和 UI 解耦**，避免第一步就被 UI 绑住。

每一步都能独立上线、独立回退。**第 1 步不改变任何机器现状**，却已经能解决「不知道
别的机器现在到底跑没跑」这个问题 —— 建议先做它。
