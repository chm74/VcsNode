# vcsNode 设计方案

多机协同：文件内容同步、进程启动/停止、状态上报。

目标形态：**每台机器安装同一个 Node 守护服务，节点之间对等，任意一台都能操作其它机器**。
没有中心控制节点；任何节点都可以作为操作入口，远程启动/停止其它机器上的项目进程、下发文件更新。

```
  任意节点执行:  vcsnode proc stop  --on 192.168.1.23:47820 --service web
                vcsnode deploy     --to 192.168.1.2x --from ./dist
```

前提：所有机器在同一网段、UDP 广播可互相发现、彼此 HTTP 可达。

> 保留的兼容路径：若将来需要跨网段，可在配置中把某一节点指定为「汇聚节点」承担 Hub 职责。
> 这是**可选模式**，不是默认架构——默认永远是对等。

---

## 0. 产品定位

**一句话**：面向「不能/不想容器化」的多台机器，把「一份代码」和「跑它的进程」绑成一个可远程同步、可回滚的服务实例。

### 0.1 管理单元

不是「进程」，也不是「文件」，而是：

```
服务实例 (Service Instance) = 节点(Node) + 服务(Service) + 版本(Release) + 进程(Process)
```

这条是它区别于其它工具的根本。把版本和进程绑在一起，才能得到真正的原子同步：
**换版本 = 同步到新目录 → 停旧进程 → 起新进程 → 指针切换 → 失败自动回滚旧版本。**

### 0.2 与现有工具的边界

| 工具 | 进程守护 | 多机集中控制 | 文件下发 | 版本化回滚 |
|---|---|---|---|---|
| PM2 / supervisord / systemd | ✅ | ❌ 单机 | ❌ | ❌ |
| Ansible / Salt | ❌ 无长期状态 | ✅ | ✅ 一次性 | ❌ |
| rsync / Syncthing / lsyncd | ❌ | 部分 | ✅ | ❌ |
| Capistrano / Deployer | ❌ 退出即失管 | ✅ 推送式 | ✅ | ✅ |
| k8s / Nomad | ✅ | ✅ | 需镜像 | ✅ |
| **vcsNode** | ✅ | ✅ 长连接+状态 | ✅ 增量 | ✅ |

差异点只有两个，但要守住：
1. **长连接 + 节点侧持久状态**（Ansible 是发完就忘，无法回答「现在到底跑没跑」）。
2. **零基础设施**：目标机只要有 Node，不需要 Docker、不需要 SSH 免密、不需要开入站端口。

### 0.3 该有的形状

三个对象：`Node`（机器）、`Service`（服务模板）、`Release`（版本，= 一台/一组机器上的文件快照）。
六个动词：`deploy`（同步）、`start`、`stop`、`status`、`rollback`、`logs`。

节点侧目录约定（借鉴 Capistrano，天然支持回滚）：

```
/srv/app/
  releases/20261022-101500/     # 每次同步一个新目录，只增不改
  releases/20261021-093000/
  current -> releases/20261022-101500    # Linux 软链；Windows 用 current.txt 指针
  shared/logs/                  # 跨版本保留
  shared/data/
```

### 0.4 明确不做

- ❌ 不做容器编排、调度、自动扩缩容、服务发现、流量接入（那是 k8s 的地盘）
- ❌ 不做通用配置管理（不管 nginx.conf 的幂等收敛，只推「应用目录」）
- ❌ 不做 CI（不编译、不跑测试，只接收产物）
- ❌ 不做多节点共识（无中心架构下不需要 Raft/Paxos；状态权威在各自节点）

### 0.5 唯一需要现在决定的岔路

| | 指令式 | 声明式 |
|---|---|---|
| 形态 | 发命令："在 web-1 启动 web" | 写目标："web-1 应运行 web@v123" |
| 执行者 | 发起节点转发 | 发起节点比对后下发 |
| 复杂度 | 低 | 中（要处理漂移、幂等、状态收敛） |

**推荐：指令式为主（MVP），声明式作为上层封装**。任意节点执行 `vcsnode deploy --to ... --release v123` 即指令式；
在此之上提供 `vcsnode reconcile --plan ./cluster.yml` 做一次性的期望状态对齐（**手动触发，不做后台死循环 reconcile**，避免一次配置写错导致全网连锁重启）。

## 1. 总体架构

**对称对等**：每台机器跑同一个守护进程，角色由「谁发起这次操作」临时决定。

```
            UDP 广播发现（同网段，每 5s）
   ┌──────────────┬──────────────┬──────────────┐
   ▼              ▼              ▼              ▼
┌─────────┐   ┌─────────┐   ┌─────────┐   ┌─────────┐
│ Node A  │   │ Node B  │   │ Node C  │   │ Node D  │
│─────────│   │─────────│   │─────────│   │─────────│
│ daemon  │   │ daemon  │   │ daemon  │   │ daemon  │
│ CLI     │   │ CLI     │   │ CLI     │   │ CLI     │
└────┬────┘   └────┬────┘   └────┬────┘   └────┬────┘
     │◄──────── HTTP RPC：启停进程 / 查状态 / 拉日志 ──────►│
     │◄──────── HTTP blob：文件直传（发起方即源）──────────►│
```

每个节点的 daemon 同时具备三种能力，按需激活：

| 能力 | 说明 |
|---|---|
| **服务端** | 接受 RPC（启停进程、查状态、拉日志），提供 blob 供他人下载 |
| **客户端** | 向其它节点发 RPC、拉 blob |
| **编排器** | CLI 触发多机 deploy 时，负责批次推进、失败处理、结果汇总 |

同一份代码，没有 master/worker 之分。A 可以让 B 启动进程，B 也可以让 A 启动进程。

**三条链路**

| 链路 | 协议 | 用途 |
|---|---|---|
| 发现 | UDP 广播（47820） | 节点互相感知；静态 seed 兜底 |
| 控制 | HTTP/1.1 RPC + SSE | 指令、查询、日志与进度流 |
| 数据 | HTTP | 文件传输、Range 断点续传 |

> 为什么控制面用 HTTP RPC 而不是 WS 全互联：控制本质是请求/响应，只有日志和进度需要流式，SSE 已经够用，
> 且自带断线重连。N 个节点全互联保持 WS 是 N² 条连接，纯属浪费。

### 1.1 去掉中心节点带来的一处关键变化：锁必须下沉

有 Hub 时，可以由 Hub 统一调度避免冲突。没有 Hub 后，**并发控制只能放在被操作的那台机器上**：

- 每个节点维护自己的**节点级互斥锁**（同一时刻只执行一个任务）。
- 两个节点同时向 C 下发 deploy → C 直接拒绝第二个（`409 node busy`），而不是让两边自己协调。
- 这就是「**每个节点是自己状态的唯一权威**」：不需要分布式锁、不需要共识算法、不需要 Raft。

同理，任务租约（lease）也由目标节点签发：

```
发起方: POST /rpc/task   → 目标节点检查锁，成功则返回 {taskId, leaseTtl: 60s}
发起方: POST /rpc/heartbeat → 续租
发起方崩溃 → 租约到期 → 目标节点清理工作目录、标记任务中断（不会留下孤儿进程）
```

### 1.2 无中心下的真实取舍

| 得到 | 失去 |
|---|---|
| 无单点故障，任何机器都能操作 | 没有全局视图，查状态要逐个问（并行即可，几十台无压力） |
| 部署零依赖，装完就能用 | 权限控制没有中心裁决点 → 必须靠每节点本地 ACL |
| 天然支持「随手从任意机器发版」 | 发起方崩溃会中断批次推进（靠租约兜底，不留脏状态） |

### 1.3 变体：指定主节点（推荐作为默认形态）

现实中运维的心智通常是「有一台主控机，从它统一发版」。这不需要额外的 Hub 服务，只需配置一个角色：

```yaml
node:
  id: node-1
  role: primary          # primary | member
  bind: 0.0.0.0:47820
cluster:
  primary: 192.168.1.10:47820
  secret: ${CLUSTER_SECRET}
  allowedPeers: 192.168.1.0/24
```

**主节点是「逻辑角色」，不是「特殊服务」**——同一个二进制、同一套协议，换个 `role` 而已。
任何节点都能被配置成 primary，切换成本是改配置 + 重启（或热切换），因此不存在「主节点机器坏了系统就报废」。

#### 主节点承担什么

| 职责 | 说明 |
|---|---|
| 唯一同步源 | 只有主节点能发起写操作；成员只提供只读查询 |
| 集群视图 | 成员每 10s 上报 `{release, health, load}`，主节点落 SQLite，可做漂移检测 |
| 批次编排 | 决定 rolling 分组、失败是否继续 |
| 写权限闸门 | 成员侧配置 `allowWrite: [primary]`，非主节点的写请求一律 403 |

这套设计把安全模型**大幅简化**：写入口只有一个，成员只需要认主节点，不用给每台机器配复杂的 ACL。

#### 控制 push、数据 pull

```
主节点 ──POST /rpc/task {op:deploy, releaseId}──► 成员   （控制：推）
成员   ──GET  /blob/<sha256>                  ──► 主节点 （数据：拉）
成员   ──POST /rpc/report {health, release}   ──► 主节点 （回报：推）
```

之所以成员**主动拉**而不是主节点推，收益很实在：
- 主节点不需要跟踪每条传输的进度，只等最终回报
- 成员天然并发拉取，主节点只做入口限流
- 断点续传由拉取方实现，逻辑集中在一处
- 主节点中途崩溃，成员拉完手上这批就停，不会写出半截文件

#### 带宽：rolling 天然解决扇出问题

10 台机器按 25% 分批，同一时刻只有 2~3 台在主节点拉文件。
200MB 产物 × 3 ≈ 5s 一批，四批约 20s 完成全量更新——**不需要两级分发**。

#### 自举问题：主节点怎么更新自己

主节点不能自己停自己。方案（三选一，推荐第一种）：

1. **延迟重启**：切换 `current` 指针 → 启动新版本子进程 → 旧 daemon 优雅退出（新进程接管端口）。
2. **服务管理器兜底**：`systemd` / `nssm` 配置 `Restart=always`，daemon 退出后自动被拉起走新代码。
3. **外部 updater**：一个极小的独立进程，只负责重启 daemon 本身。

#### 主节点挂了会怎样

| 影响 | 不受影响 |
|---|---|
| 无法发起新的发版 | 已运行的项目进程照常跑 |
| 成员心跳上报堆积 | 成员之间仍可互相启停/查状态（对等能力保留） |
| 需要人工 promote 新主节点 | 回滚仍可在各节点本地完成 |

**这就是「主节点 + 保留对等能力」相对「独立 Hub」的核心优势**：降级而不是瘫痪。

## 2. 进程模型

**Node 守护进程（每台机器一个）**
- 单进程常驻（Linux: systemd；Windows: NSSM/winsw）。
- 内部模块：`RpcServer`（HTTP 控制面）、`BlobServer`（文件服务）、`Supervisor`（进程）、
  `Watcher`（可选，监听源目录）、`SyncEngine`（清单/传输/落盘）、`TaskQueue`（节点锁 + 租约）。
- 状态落本地 SQLite（任务历史、release 记录、审计），重启可恢复。

**CLI（同一台机器上的另一个入口）**
- 通过本地 daemon 或直接 HTTP 操作任意节点；也可在无 daemon 的机器上作为纯客户端使用。
- 多机 deploy 时 CLI 进程担任编排器，按批次调用各节点的 RPC。

## 3. 协议设计

统一信封（WS 文本帧）：

```ts
type Envelope<T> = {
  v: 1,
  id: string,          // uuid，用于 ack / 幂等
  type: string,
  ts: number,          // 毫秒
  nodeId?: string,
  replyTo?: string,
  payload: T,
}
```

### 3.1 指令集

| type | 方向 | payload 要点 |
|---|---|---|
| `agent.hello` | A→H | `{agentId, token, version, os, arch, caps[]}` |
| `agent.welcome` | H→A | `{sessionId, serverTime, limits}` |
| `agent.heartbeat` | A→H | `{load, procs: n, syncState}` |
| `proc.start` | H→A | `{taskId, service: "web", args?, env?, cwd?}` |
| `proc.stop` | H→A | `{taskId, pid?, service?, signal?, timeoutMs}` |
| `proc.list` | H→A | `{}` |
| `proc.logs` | H→A | `{pid, tailBytes}` |
| `fs.manifest` | A→H | `{root, entries[{p,size,mtime,mode,sha256}], page}` |
| `fs.plan` | H→A | `{filesToSend[], filesToFetch[], deletes[]}` |
| `fs.apply` | H→A | `{files[{p, blobId, sha256, mode}], mode:"atomic"}` |
| `fs.event` | A→H | `{changes[{p, op:"add\|change\|unlink"}]}` |
| `task.ack` | 双向 | `{taskId, ok, result, error?}` |

大文件的三段式：`fs.plan` 定差异 → HTTP 传 blob → `fs.apply` 落盘（临时文件 + rename）。

### 3.2 幂等与可靠性
- 每条指令带 `taskId`（Hub 生成），Agent 维护最近 N 条已执行任务的 LRU，重复到达直接返回缓存结果。
- 所有 fs 写入使用 `tmp-<taskId>` → `fsync` → `rename`，避免半写文件被业务读取。
- 指令默认超时（如 30s），超时进入 `unknown` 状态，由 Agent 上报实际状态纠正。

## 4. 文件同步算法

核心原则：**清单驱动 + 内容哈希判定**，不要依赖 mtime（跨机时钟漂移 + 时区 + FAT 精度）。
同步的**粒度是「目录快照」**，不是「文件事件流」—— 后者会出现「目标端读到一半新一半旧」的中间态。

### 4.0 传输拓扑：同网段 → 数据面网状直连

**前提：所有机器在同一网段、互相可达。** 控制面仍是星型（Agent → Hub），但数据面改为 Agent 直连：

```
  source agent ──HTTP GET /blob/<sha256>──► target1
               ──HTTP GET /blob/<sha256>──► target2
               ──HTTP GET /blob/<sha256>──► target3
```

为什么直连优于 Hub 中转：源节点本来就有文件，直连**省掉了往 Hub 上传的那一程**。千兆内网实测约 118 MB/s，200MB 产物 ≈ 1.7s 传完，远比「先传 Hub 再扇出」快。Hub 只在两种情况下兜底：源节点不可达、或跨网段。

**节点发现**：UDP 广播信标（固定端口 47820），每 5s 广播 `{agentId, ip, port, version, load}`；Hub 也广播自身。必须同时支持**静态 seed 列表**兜底——企业交换机可能开启端口隔离/禁广播，纯自动发现会静默失败。

**简化（重要）**：带宽不再稀缺，因此**放弃 CDC / 块级 delta**。全量 `tar.zst` + sha256 秒传即可，省下的复杂度很可观。瓶颈从「带宽」转移到「CPU 与磁盘」：
- 哈希与压缩走 `worker_threads` 池（默认 = CPU 核数 / 2，上限 8）
- 并发 blob 数可提到 8~16（内网不再需要激进限速，但仍设上限防打满）

**扇出**：源节点作为种子服务 N 个目标。目标超过 ~8 台且产物 > 500MB 时，改为两级分发（源 → 3 台中继 → 其余），避免源网卡上行成为瓶颈。

**回滚免费**：`releases/` 目录本身就留在节点上，回滚只是切指针，**零传输**。Hub 的 release archive 只用于「新节点首次引导」和「节点磁盘被清空后的重建」。

### 4.1 清单（manifest）
```ts
type Entry = {
  p: string        // 相对路径（POSIX 分隔符，统一 normalize）
  size: number
  mtimeMs: number
  mode: number
  sha256: string   // 小文件直接算；大文件按块算
  chunks?: string[] // 大文件：CDC 分块哈希
}
```
- 首次同步、或 size/mtime 变化时才重算 hash（缓存落 `.vcscache`）。
- 清单分页（如 2000 条/页），避免单条消息过大。

### 4.2 差异算法
1. Hub 保存每个 `(node, root)` 的上次清单作为 **base**。
2. 对比 source / target / base 得到三种操作：`create`、`update`、`delete`。
3. 冲突（双端都改）：按策略处理
   - `source-wins`（默认，用于「下发配置」场景）
   - `newer-wins`（比较 mtime，容忍漂移 ±2s）
   - `manual`（挂起，等人工确认）
4. 删除用**墓碑 + 白名单**：只删上次清单里存在、本次源端消失的文件，绝不递归删未知文件。

### 4.3 传输优化（分阶段）
- **P1**：整文件传输 + zstd 压缩（Node 22 内置 `zlib.zstdCompress`）。
- **P2**：大文件分块（4MB），块级哈希比对，只传变化块 → 近似 rsync。
- **P3**：CDC（内容定义分块），插入内容不再导致后续全量块错位。
- 可选：直接支持 `rsync --delete` / `rclone sync` 作为后端（跨平台、成熟、省事），Hub 只负责调度与审计。**如果部署环境已装 rsync，建议直接走这条路，自己只做调度层。**

### 4.4 触发方式
- **手动**：CLI `vcsnode sync push ./dist --to all`
- **监听**：chokidar，`awaitWriteFinish` + 300ms 防抖，批量合并成一次任务
- **定时**：cron 表达式（配置在 Hub）
- **提交后**：git post-commit hook

### 4.5 排除规则
`.vcsignore`（gitignore 语法，用 `ignore` 包解析）：
```
node_modules/
.git/
*.log
data/*.db
```
默认硬保护：`.env*`、`*.pem`、`.ssh/` 除非显式允许。

### 4.6 多机更新编排：把「更新」当成一次事务

N 台机器的内容更新不是 N 次同步，而是**一次以版本为单位的事务**：
要么目标集合全部收敛到 `releaseId`，要么整体回滚到上一个版本。

Hub 侧维护两张状态，一切逻辑都围绕「让 actual 收敛到 desired」展开：

```sql
node_state (node_id, desired_release, actual_release, actual_health, updated_at)
```

状态机（每台机器独立推进）：

```
pending → preflight → transferring → verifying → activating → healthcheck → converged
                                             ↘ failed → rolledback
```

**批次（strategy）**

| 策略 | 适用 | 说明 |
|---|---|---|
| `parallel` | ≤3 台 / 测试环境 | 全量同时更新，最快，炸就是全炸 |
| `rolling`（默认） | 生产 | 按 25% 一批，本批全部 `converged` 才进下一批 |
| `canary` | 关键服务 | 先 1 台，观察窗口 60s 无异常再放量 |

失败处理：`fail-fast`（默认，停止后续批次并对本批回滚）或 `best-effort`（跳过失败机继续）。失败的机器保留当前版本、标记 `failed`，不影响已经健康的机器。

**幂等**：同一 `(node, releaseId)` 重复 deploy 必须直接返回成功且不做任何 IO —— 运维一定会重复点。传输阶段可重试，`activating` 已成功的机器绝不重复执行。

**互斥**：同一节点同一时刻只允许一个更新事务（节点级锁，租约 + 心跳续期），否则两次并发 deploy 会交错写 release 目录。

**收敛 ≠ 成功**：Agent 报「文件到位」只代表 `verifying` 完成。必须再过 `healthcheck`（HTTP 探活 / 端口监听 / 自定义命令，超时即失败）才算 `converged`。否则你会得到一个「文件正确但进程起不来」的假成功。

### 4.7 该传什么、不该传什么

| 类别 | 处理 |
|---|---|
| 构建产物 `dist/`、静态资源 | ✅ 同步 |
| `node_modules/` | ❌ 禁止同步。平台/架构/原生模块不一致，改为目标机执行 `npm ci --omit=dev` |
| `.git/` | ❌ 不同步 |
| 日志、上传文件、数据库 | ❌ 不随 release 走，放 `shared/` 跨版本保留 |
| 每机不同的配置 | ⚠️ 用模板 + 变量渲染（`{{node.id}}`、`{{env.PORT}}`），不要手工维护 N 份 |
| 密钥 | ❌ 不进 blob 存储，走环境变量/密钥文件下发通道 |

**内容更新 ≠ 重启进程**，要按内容类型分流：

| 改了什么 | 动作 |
|---|---|
| 只改静态资源 / 模板 | 不重启，发 `SIGHUP` 或调 reload 接口 |
| 改了服务端代码 | 快照切换 + stop → start（Node 单实例无法热替换，会有秒级中断） |
| 改了依赖 | 目标机 `npm ci` 后重启 |
| 只改 `shared/` 数据 | 不触发部署，走单独的配置下发 |

## 5. 进程管理细节

### 5.1 启动
- **只允许启动「预注册的服务模板」**，不接受任意命令行。这是整个系统最重要的安全设计。
  ```yaml
  # hub 侧配置，下发到 agent
  services:
    web:
      cmd: node
      args: ["dist/server.js"]
      cwd: /srv/app
      env: { NODE_ENV: production }
      restart: on-failure
      stopSignal: SIGTERM
      stopTimeoutMs: 10000
  ```
- `spawn(cmd, args, { cwd, env, detached: !win32 })`，不经过 shell，规避注入。
- 日志：stdout/stderr 管道 → 环形缓冲（内存 500 行）+ 滚动文件 `logs/<service>-<date>.log`。
- Windows：`detached: true` + `windowsHide: true`，PID 记录为 taskkill 树根。

### 5.2 停止
```
SIGTERM → 等待 stopTimeoutMs → SIGKILL
Windows: taskkill /PID <pid> /T /F
```
- 停止前先禁用 `restart: on-failure`（否则会被守护逻辑拉起来 —— 常见坑）。
- 进程状态机：`stopped → starting → running → stopping → stopped | crashed`，崩溃单独标记，与人工停止区分。

### 5.3 看护
- Agent 重启后通过 pidfile 回收/清理孤儿进程（校验 pid 对应 cmdline，避免 PID 复用误杀）。
- 资源限制（可选）：Linux 用 `cgroup v2` / `ulimit`，Windows 用 Job Object。

### 5.5 与文件同步的协同：三条能力合成一个 deploy 事务

「启停进程」和「同步文件」不是两个并列功能，它们的**交叉点**才是系统的主体。所有操作统一为一种东西——**节点级任务**，共用一把锁。

#### 三种任务类型

| 类型 | 做什么 | 碰进程吗 | 典型用途 |
|---|---|---|---|
| `sync` | 只同步文件到 `releases/<ts>/` 并切指针 | ❌ | 静态资源、脚本、模板 |
| `proc` | 只启停/重启/查日志 | ❌ 不碰文件 | 手动运维、拉起崩掉的服务 |
| `deploy` | 同步 + 切指针 + 重启 + 探活 | ✅ | 同步新版本 |

三者**共用同一个执行器与同一把节点锁**：同一节点同一时刻只允许一个任务，不同节点完全并行。这就是「同时满足」的真正含义——**串行化在节点内，并行化在节点间**。

#### 为什么同步不能覆盖运行中的目录

进程运行时持有文件句柄。在 Windows 上对正在被读取的 `.node` / `.dll` 做 `rename`/`delete` 会直接 `EPERM`/`EBUSY`，Linux 上则可能出现「进程读到一半新旧混合」的撕裂状态。

所以 `releases/` + `current` 指针这个结构**不只是为了回滚**，它是让「进程运行中也能安全同步」的前提：传输永远写新目录，运行中的进程完全不受影响。

#### 正确顺序与停机时间

```
t=0.0s   transfer     传到 releases/<ts>/，旧进程照常服务
t=1.7s   verify       逐文件 sha256 校验
t=2.0s   stop         SIGTERM（等 stopTimeoutMs）
t=2.3s   wait-port    轮询端口直到释放（否则立刻 start 会 EADDRINUSE）
t=2.4s   swap         current 指针切换（原子）
t=2.5s   start        新进程起来
t=3.2s   healthcheck  探活通过 → converged
```

**停机窗口只有 `stop → healthcheck` 这一段（约 1 秒）**，传输和校验都在旧进程存活期间完成。这就是「预热式同步」——把不可避免的中断压缩到最小。

反过来，如果先停进程再同步，停机时间 = 传输时间 + 校验时间，200MB 就是 2 秒以上，而且传输一旦失败，服务已经停了。

#### 五个必须显式处理的交叉点

1. **cwd 必须指向 `<app>/current`，不能指向具体 release 路径。** 否则切了指针、重启后进程仍跑旧代码（因为 cwd 还硬编码在旧目录里）。这是最隐蔽的错。
2. **端口释放要主动等待。** 进程退出 ≠ 端口空闲，`TIME_WAIT` 和未回收的子进程都会导致 `EADDRINUSE`。策略：轮询 `connect` 直到 `ECONNREFUSED`，上限 5s，超时则 `SIGKILL` 整个进程树。
3. **文件监听必须排除 `releases/` 与 `current`。** 否则 Agent 自己写同步目录会触发 watcher → 又发起一次同步 → 无限循环。`.vcsignore` 里把 `releases/`、`.vcs/`、`.vcsbak/` 设为**硬保护**（不可被配置覆盖）。
4. **回滚同样是进程操作。** `rollback` = 切指针 + 重启 + 重新探活，不是纯文件切换。探活失败要标记 `unhealthy` 并告警，不能报成功。
5. **手动 `proc.stop` 会被 deploy 打断/覆盖。** 因为共用节点锁，第二个任务排队或直接拒绝（`409 node busy`）。禁止等待式排队超过 30s，否则用户以为卡死。

#### 最终状态判定

一次 `deploy` 只有在「文件 hash 全对 + 指针已切 + 进程 running + healthcheck 通过」四项同时成立时才报 `converged`。任何一项不成立都进入 `failed`，并按策略回滚到上一版本（同样走完整的 restart + healthcheck）。

## 6. 安全

| 项 | 方案 |
|---|---|
| 传输加密 | 生产必须 `wss://` + `https://`；自签场景用私有 CA |
| 认证 | 每台 Agent 一个 `agentId + secret`；`hello` 用 HMAC 签名 `(agentId, ts, nonce)`，Hub 校验 ±60s 窗口 + nonce 去重 |
| 授权 | 路径白名单（`allowedRoots`），`path.resolve` 后校验前缀，防 `../` 逃逸；符号链接需 `realpath` 二次校验 |
| 指令白名单 | 只能启停配置中存在的 service，只能同步 allowedRoots 下的路径 |
| 审计 | 所有指令落库：who / when / node / action / params / result |
| 最小权限 | Agent 用专用系统用户运行，不 root |

## 10. 主要风险与对策

| 风险 | 对策 |
|---|---|
| Windows 文件被占用导致 rename 失败 | 重试 + 退避；`fs.rm` 失败回退 `copy+truncate`；提示占用进程 |
| 大小写/路径分隔符差异（Linux↔Windows） | 内部统一 POSIX 相对路径，落盘时按平台转换；Windows 上大小写冲突检测 |
| 大量小文件性能（10w 文件） | 清单分页 + 流式解析 + 批量 stat；hash 并发池限 8 |
| 双端同时修改造成数据丢失 | 写入前保留 `.vcsbak/<ts>/path`，保留最近 N 版 |
| Agent 拿到任意执行能力 | 服务模板白名单，禁用 shell，路径白名单 |
| Hub 单点 | MVP 接受；生产加 systemd 自动重启 + SQLite 定时备份 |

## 11. 需要先确认的问题

1. **控制方式**：Hub 集中（推荐）还是纯 P2P（无中心）？
2. **被控机器网络**：✅ 已确认——同一网段。控制面星型（WS 反连 Hub），数据面网状直连。
3. **同步方向**：单向下发（部署场景）还是双向（协作场景）？双向需要冲突 UI。
4. **进程范围**：固定几个服务，还是要能跑任意命令？（强烈建议前者）
5. **规模**：几台 / 几十台 / 几百台？决定是否引入 Redis、分片队列。
