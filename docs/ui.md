# vcsNode 界面说明（页面原型）

> 2026-10-26 · 原型阶段 · **只有界面，没有后端**
>
> 打开方式：直接双击 `ui/index.html`（零依赖、无构建），或
> `node tools/serve-ui.mjs` 后访问 `http://localhost:47830/`。
> 设计依据 `architecture.md`，术语以该文档 §9 为准。

---

## 1. 页面结构

```
┌─────────────────────────────────────────────────┐
│ 顶栏：集群摘要 · 时钟 · 用户                     │
├────────┬────────────────────────────────────────┤
│ 总览    │                                        │
│ 待同步区 │              主区域                    │
│ 同步记录 │                                        │
│ 启停记录 │        （右侧抽屉：组件详情）            │
│ 配置    │                                        │
│ 事件    │                                        │
└────────┴────────────────────────────────────────┘
```

六个视图 + 一个抽屉 + 两个弹层，全部单页切换，不刷新。

| # | 视图 | 回答什么问题 | 主要动作 |
| --- | --- | --- | --- |
| 1 | 总览 | 现在四台机器上哪些东西活着 | 点格子看详情、启停 |
| 2 | 待同步区 | 98 上改了什么、这次要发什么 | 勾选、跳过、预同步、切换上线 |
| 3 | 同步记录 | 每一版落在哪、能不能回退 | 回退 |
| 4 | 启停记录 | 谁在什么时候启停过、成没成、为什么失败 | 按节点/组件/动作/结果筛选 |
| 5 | 配置 | 四台的路径/端口配得对不对 | 探测、保存并下发 |
| 6 | 事件 | 成员连没连上、指令和回执走没走通 | 按节点/动作过滤 |

## 2. 各页要点

### 2.1 总览

**节点卡片**（一行四张）：在线状态、运行/异常/已停数量、在线时长、一句话提示。

提示位专门用来放「需要人看一眼」的事，例如：

- 145：`1 个组件假活：generateclient 未连上 207:3601`
- 149：`控制面连接已断开 4 分钟`

**组件矩阵**：行 = 组件，列 = 节点。虚线 `—` 表示该节点不部署这个组件（不是故障）。

**列的顺序**固定为：同步源（98）永远第一列，其余按 `config/vcsnode.yaml` 里 `nodes:` 的**书写顺序**
（现在是 98 · 149 · 207 · 145）。不按 IP 排序 —— 试点机 149 要挨着 98，方便两边对照。
要调整顺序就改配置里节点的排列，界面和接口都跟着走。

陷阱：把「没部署」画成「已停止」会让人以为出了故障，所以必须用两种不同的视觉。

**抽屉**（点格子打开）：状态、PID、连接/端口、工作目录、启动方式、更新策略、操作按钮。
启动方式显示 `cmd + args`，下面一行显示**解析后的绝对工作目录**（`localRoot` + `start.cwd`），
避免「`dotnet .\X.dll` 到底在哪个目录跑」只能靠猜。
假活和孤儿会多出一段「为什么」，直接说明原因和下一步。

**操作按钮（M1：启动 / 停止 / 重启都已接）**：

- **停止 / 重启**：两段式确认 —— 第一下按钮变成红框「再点一次确认停止/重启」，6 秒内再点才真的下发；
  超时自动复位。prod 上误点一下不该停服务。
- **启动**：一下就发（起一个本来没跑的服务，代价远小于误停）；已经在跑时接口返回「本来就在跑」，不会重复起。
- 下发中按钮显示「启动中… / 停止中… / 重启中…」并禁用；回执到了按真实结果提示
  （`pid` / 耗时 / 端口是否在监听或已释放 / 重启前是否在跑），抽屉和矩阵随即按新数据重画。
- 成员拒绝时原样显示原因（`not_running` / `not_ours` / `identify_mismatch` / `bad_cwd` / `port_busy` /
  `exited` / `control_disabled` …），不吞成「失败」两个字；`exited` 还会带上服务日志的尾巴。
- 同步源（98）那一列的按钮**全部禁用**，并写明「同步源由人工操作」；
  纯文件组件（`kind: asset`）也禁用（没有进程可启停）。

### 2.2 待同步区

三段式：**扫描信息 → 变更清单 → 同步影响（右侧固定）**。

- 顶部扫描条：基线版本、本次版本、扫描时间、扫描源
- 组件小结：每个组件 `+新增 ~修改 -删除` 与体积
- 文件清单：按组件分组可折叠，每行 `勾选 · 状态 · 路径 · sha256 前 8 位 · 大小 · 修改时间 · 归因组件`
- 右侧影响：目标节点、涉及组件、**落地方式**（就地覆盖：先备份、再校验 sha256）、传输量、删除项计数、**前置条件**（组件已停止）
- 确认项：数据库变更（人工）、删除项（单独确认，默认不勾）
- 两个按钮：**预同步**（M2：把文件落到成员，服务必须先停 → 见 §2.2.1）与 **切换上线**（M3，暂时只提示）

**数据从哪来**：右上角徽标说明当前是哪一种 —— `实时数据`（连上了 master，清单真实）、
`未扫描`（有服务但还没扫过）、`演示数据`（静态预览，没有后端，清单是假的）。
只有第一种能作为同步依据。没有变更时显示空状态，而不是一张空空如也的表格。
顶部还会显示读取失败的路径（例如某台机器上目录不存在），不静默吞掉。

删除行的视觉是刻意做重的：红色删除线 + 默认不勾 + 必须在右侧单独确认。
删除是唯一不可逆的动作，界面上不能和「修改」长得一样。

#### 2.2.1 预同步（M2 实际行为）

点「预同步」→ 弹确认框（组件 / 文件数 / 是否含删除 / 目标节点）→ 确认后：

1. 98 把勾选的文件复制到 `\\172.16.2.98\Tools\_vcs\releases\<relId>\`，写 `manifest.json`
2. 每台目标机从共享只读拉取 → 备份旧文件到 `C:\vcsNode\backup\<relId>\` → 校验 sha256 → 就地覆盖
3. 全绿：toast `更新完成：N 个文件 · X KB · 2/2 台已落地（0.5s），可以启动了`，
   待同步区里这批文件消失（基线推进），同步记录多一条
4. 有失败：toast 列出哪台因为什么失败，**待同步区原样保留**，修好后重发

会被拒绝的三种常见情况（都在下发前就拦，不会改一半）：

| 情况 | 界面表现 |
| --- | --- |
| 组件还在跑 | toast「更新失败：这些组件还在跑，先在抽屉里停止再更新文件：149/webapi（运行中）」 |
| 扫描源 ≠ 98 运行目录 | toast 里带 `layout_mismatch` 原文 + 该组件的两个路径 |
| 有目标机离线 | toast「… 不在线：等它连上再发（不允许只发一半）」 |

### 2.3 同步记录

表格：版本、时间、组件、节点、状态（`已落地 2/2` / `部分失败 1/2` / `失败`）、操作。
数据来自 `GET /api/ui/releases`；一条都没有时显示「还没有同步记录，去待同步区」。

**「详情」打开右侧抽屉**（和组件抽屉同一个壳），回答两个问题：**更新了哪些文件**、**什么时候落到每一台**。
数据来自 `GET /api/ui/releases/{relId}`（就是同步时的 manifest + 各节点回执）：

1. **本次更新**：文件数（`+新增 ~修改 -删除`，只显示非零项）、合计体积、组件、发起时间与总耗时、发起人、备注
2. **各节点落地**：每台一行 `节点 · 落地时间 · 文件数（删 N） · 体积 · 耗时`，失败的带原因
3. **文件明细**：每行 `动作徽标 · 相对路径 · 大小`，第二行小字 `组件 · 98 改于 … · 落地 …`（多台时显示最早 → 最晚）
   - 删除项划掉，大小显示 `—`
   - 「落地」是**节点级**时间（一次任务落一批文件，成员回执只有一个完成时刻），逐文件时间在 M3 细化

**三个时间点必须在界面上分开**，否则会误导：

| 显示 | 含义 |
| --- | --- |
| 98 改于 | 源文件在 98 上的最后修改时间（`sourceMtime`） |
| 落地 | 各节点写盘完成的时间（最早 → 最晚） |
| 发起 / 用时 | 这次同步开始的时间与总耗时 |

这些数字来自同步 **manifest**（同步当时记下来的），不是事后重新扫描推算的 ——
重扫只能得到「现在」，得不到「当时」。字段定义见 `protocol.md` §8.3。

> 没有后端（直接双击 `ui/index.html` 或用静态服务器打开）时退回演示数据，
> 抽屉底部会写明「当前为演示数据」，避免把假版本号当真。

### 2.4 配置（**已实现，可保存**）

- 顶部三张卡说明三层配置，第③层显式置灰（永不下发）
- 横幅：接上 master 时显示当前 `revision` 与最后保存时间；没有后端时显示「演示数据 · 不可保存」
- 矩阵：行 = 组件，列 = 节点，格子 = 启用开关 + 端口 + `localRoot`
- 末行是每台的共享目录（四台可能不同）；沿用全局时标注「继承全局」
- `localRoot` 为 `null` 时输入框标红、开关置灰并提示「该组件不会被启用」—— 宁可拦下，不要静默用错路径
- 改动只在本地攒着，右上角显示「N 处未保存」，可一键撤销
- 「保存配置」先弹逐条 diff（旧值 → 新值），确认后才写盘；不做静默保存
- 保存失败（端口越界、路径不合法、组件没部署）直接在 toast 里显示服务端原文，文件不动

保存成功后：主节点立刻用新配置替换内存里的那份（总览 / 矩阵抽屉里的「工作目录」「端口」随之更新，不用重启 master），
并向已连上的成员重发 `hello`，成员刷新 `node-config.json` 后立即重采样。

没有 agent 的现状下，保存只改主节点的 `config/vcsnode.yaml`，不下发；
「探测全部节点」只真的检查主节点本机路径，其余三台显示「未探测」。

> M0 的成员只是按 hello 里那份配置观测进程，配置变更**不会**同步文件、也不会启停任何服务。

### 2.5 启停记录（**已实现**）

回答「昨晚 22:13 是谁停了 145 的 mcpserver、成没成、为什么失败」。

- 顶部四张卡：今日启停次数、近 30 天失败数、最近一次失败、最近一次操作
- 表格 8 列：时间、节点、组件、动作、结果、耗时、PID、说明
  - 动作：启动 / 停止 / 重启 / 更新文件 / 异常退出（`exit`）/ 失联（`lost`，预留）
  - 结果只有两态：成功 / 失败；失败行的「说明」是原因原文（`still_alive`、`exit_1`、`timeout` …）
- 四个筛选：节点、组件、动作、结果；每页 15 条，带分页
- 数据来自 `GET /api/ui/actions`，落盘 `state\actions\YYYYMMDD.jsonl`，保留 30 天
- 「异常退出」是**进程自己没了**（崩溃/被外部杀掉）；我们主动停的不算，正常停止不会出现假的红行
- 页面**不跟 5 秒轮询重画**（否则翻到第 2 页会被打回第 1 页），要看最新的点右上「刷新」

### 2.6 事件

时间、节点、动作、详情、结果、耗时。按节点 / 动作过滤，30 天，每页 15 条。
事件记的是控制面（`connect` / `task` / `ack` / `nack` / `state` / `probe`），
「谁停了什么服务」看启停记录，两边按时间对得上。

## 3. 状态色约定

| 状态 | 文案 | 颜色 | 含义 |
| --- | --- | --- | --- |
| running | 运行中 | 绿 | 进程在，判活通过 |
| busy | 忙 | 黄 | 正在生成，禁止停/重启/切换 |
| degraded | 假活 | 黄 | 进程在，但没连上 webapi |
| orphan | 孤儿 | 紫 | 端口被占但进程不在 |
| crashed | 异常退出 | 红 | 进程不在（非人为） |
| stopped | 已停止 | 灰 | 人为停止 |
| offline | 离线 | 浅灰 | 控制面连接不存在，**不是**组件故障 |
| — | — | 虚线灰 | 该节点不部署 |

红/黄/紫三种「不正常」必须能一眼分开：处置完全不同，混在一起看会做错动作。

## 4. 与真实接口的对应

数据来源是「能用真的就用真的，不能用就退回演示数据」，右上角徽标会说明当前是哪种：

| 徽标 | 含义 |
| --- | --- |
| 实时数据 | 连上了 master，清单 / 配置都来自真实文件 |
| 未扫描 | 有 master，但还没建立基线 |
| 演示数据 | 静态打开或后端不可用，数据是假的 |

| 页面区块 | 真实接口 |
| --- | --- |
| 节点卡片 / 组件矩阵（**已实现**，M0） | `GET /api/ui/nodes` |
| 节点卡片右上角徽标 | 有数据 = `节点数据 · 实时`；接口失败 = `演示` |
| 抽屉里的启停（**已实现**，M1） | `POST /api/ui/task {action:"start"\|"stop"\|"restart"}` |
| 待同步区（**已实现**） | `POST /api/ui/scan`、`GET /api/ui/pending` |
| 待同步区（草稿编辑，未实现） | `PATCH /api/ui/release/pending/{id}`（现在勾选只存在浏览器内存里，刷新就回到默认：新增/修改全选、删除不选） |
| 预同步（**已实现，M2**） | `POST /api/ui/stage` |
| 切换上线（未实现，M3） | `POST /api/ui/release/commit`（现在点了只提示「还没接」） |
| 同步记录 / 列表（**已实现**） | `GET /api/ui/releases` |
| 同步记录 / 详情（**已实现**） | `GET /api/ui/releases/{relId}` |
| 同步记录 / 回退（未实现） | 现在按 `runbook.md` §9.5 从成员 `backup\<relId>\` 手工拷回 |
| 配置（**已实现**） | `GET/POST /api/ui/config`、`POST /api/ui/config/probe` |
| 配置回退（未实现） | `POST /api/ui/config/rollback` |
| 启停记录（**已实现**） | `GET /api/ui/actions?page=&size=&node=&component=&action=&result=` |
| 事件（**已实现**） | `GET /api/ui/events?page=&size=&node=&action=&result=` |

契约见 `protocol.md`。

## 5. 这版原型刻意没做的

| 没做 | 原因 |
| --- | --- |
| 代码 diff 预览 | 待同步区先证明「清单对不对」，逐行 diff 是第二步 |
| 暗色主题 | 现场是白天办公环境，浅色够用；要做的话只换 CSS 变量 |
| 移动端适配 | 运维在电脑上操作，窄屏只做到「不塌」 |
| 权限/登录 | 内网单用户，暂不做；真要做得先定账号体系 |
| 一键全部停止 | **不做**。这种按钮在误触时的代价，远大于它省下的几秒 |
| 同步进度条 | 预同步是一个同步请求，落地完才返回；按钮只显示「更新中…」。要实时进度得把 stage 改成异步任务 + 轮询/SSE |
| 勾选状态落盘 | 现在刷页面就丢（默认新增/修改全选、删除不选）。`PATCH /api/ui/release/pending/{id}` 还没做 |

## 6. 待确认的界面问题

| # | 问题 | 影响 |
| --- | --- | --- |
| 1 | 待同步区要不要**点开看代码 diff**？ | 要的话工作量翻倍（需要 diff 渲染 + 语法高亮） |
| 2 | 组件矩阵是否需要「按机器看」的第二种视图（一台机器一张卡，列出全部组件）？ | 现在只有一个矩阵，机器多时行数会变长 |
| 3 | 「预同步 / 切换上线」这两个词现场能接受吗？ | 现在刻意避开了 STAGE / COMMIT 这种实现词。注意 M2 的「预同步」已经是**会真的改文件**（就地覆盖），不再是「先摆好但不动」——是否要改叫「更新文件」？ |
| 4 | 同步是否需要「定时窗口」（比如只在夜间允许切换）？ | 影响 COMMIT 的前置校验 |
| 5 | 事件页要不要保留完整日志下载？ | 影响日志存储与脱敏策略 |
